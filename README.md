## `01 / fieldnotes`

I study biology and build software to make sense of it.

Most of my work lives somewhere between bacteriophage genomes, scientific
workflows, and the infrastructure underneath them. I like taking a process
that is manual, opaque, or difficult to repeat and turning it into something
inspectable, reusable, and documented.

Sometimes that means a Snakemake workflow. Sometimes it means an R visualization.
Sometimes it means figuring out why a service stopped working on a repurposed server.

Different systems. Similar questions.

## `02 / active cultures`

### Phantom
Developing a Snakemake-based phage-analysis workflow, with an emphasis on
reproducibility and making the path from inputs to results easier to follow.

### Tools for the questions after annotation
Building R and Python tools for phage visualization, comparative genomics,
and post-annotation analysis—because generating an annotation is not the same
thing as understanding a genome.

### A lab outside the lab
Working with Linux, Proxmox, containers, and self-hosted services.
Part useful infrastructure, part ongoing experiment in how systems fit together.

## `04 / open questions`

- How can comparative genomics become more interpretable, not just more automated?
- How do we build research software that someone else can actually reproduce?
- Where can mathematical modeling and machine learning help explain biological systems?
- How much infrastructure can I understand by building—and occasionally breaking—it?

Currently exploring systems biology, scientific Python package design,
software testing, and Kubernetes/GitOps.

## `05 / operating principles`

> Make it work. Understand why it works. Make it reproducible.

- Prefer inspectable tools and explicit assumptions.
- Treat documentation as part of the project.
- Automate repeated work without hiding the underlying biology.
- Build for the next person—including future me.
- Leave room for experiments that are useful mainly because they teach something.
